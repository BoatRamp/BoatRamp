# PLAN — let a `scoped` route write a declared-global (`unscoped`) table (#503)

**Branch:** `scoped-unscoped-write` · **Base:** v0.5.7 (`63dd275`, edition 2024 / Rust 1.91)
**Status:** APPROVED — 3-role panel (Backend/Senior Architect + UX + Security) all **PASS-WITH-CONDITIONS**; owner approved implementation 2026-09-26. Security-sensitive tenancy-boundary change → implement behind a Security-review loop + a mutation-verified **cross-surface** gate, then version-bump → release.

## Problem (verified against code)
A `scoped` route (`tenancy: read:"own", write:"own"`) is **refused** when it writes a table declared `unscoped` — `crates/boatramp-core/src/orm.rs:730`, `Scope::write_target` → `ResolvedScope::Unscoped => Err(OrmError::UnscopedWrite(..))`, unconditional. The deny-by-default is deliberate: `crates/boatramp-types/src/tenancy.rs:526-530` documents `Unscoped` = global READ, **write deny-by-default** ("a shared-data write is a cross-tenant blast"), archetype `countries` (read-only reference). The only workaround, `write:"all"`, co-widens READS → breaks per-tenant isolation. Canonical need: OAuth/OIDC social-login `/start` reads per-tenant provider config (`read:"own"`) AND must write a genuinely-global CSRF `oauth_state` (shared-callback topology recovers tenant from `state`, so the table has no tenant dimension). The gap: no middle ground between fully-isolated `own` and fully-cross-tenant `all`.

## Approved design — OR two independent opt-ins
A guest write of table `T` by route/handler/consumer `R` is allowed **iff** (evaluated fresh in the single choke point `Scope::write_target`, and mirrored on the raw-SQL surface — see CRITICAL below):
1. `T` is a per-tenant kind (`Tenant`/`TenantKeyed`/`TenantOrSession`/`TenantOrBase`) → existing scoped stamp (**UNCHANGED**); or
2. `!R.is_target()` **and** `T` is declared **write-global** → allow, no tenant stamp (the *general* path — any scoped route); or
3. `!R.is_target()` **and** `T` resolves to plain `Unscoped` **and** `T ∈ R.unscoped_writes` → allow, no tenant stamp (the *strict* path — only listed routes);
else **deny** (plain `Unscoped` not listed / undeclared / no-principal) — fail-closed. `read:"own"` is **untouched** in every case.

The developer chooses per table: **sensitive / few writers → keep `unscoped`, list it on the route(s) (`unscoped_writes`)** (least-privilege, default recommendation); **genuinely-global / many writers → declare it write-global** (one declaration).

### Spelling (panel-reconciled — do exactly this)
- **Wire / config:** extend the existing `unscoped` kind with a `writable` flag — `TableScope::Unscoped { writable: bool }` (`#[serde(default, skip_serializing_if = ..)]`, default `false`). A pre-#503 `{"kind":"unscoped"}` MUST deserialize byte-identically to `writable:false` (add a round-trip test). **Do NOT** add a `Shared` kind — it collides with `TenantOrBase`'s "shared base" read model (UX reject).
- **Internal resolved:** map `Unscoped { writable:true }` to a **distinct `ResolvedScope::SharedWritable`** variant (NOT reuse `ResolvedScope::Unscoped`). This makes the compiler force every match arm to be revisited — the exhaustiveness is a security property (Security explicitly wanted this over a silent fall-through). `Unscoped { writable:false }` → `ResolvedScope::Unscoped` (today's behavior).
- **Route field:** `unscoped_writes: Vec<String>` as a **sub-field of `Tenancy::Scoped`** (`crates/boatramp-types/src/tenancy.rs:336`), `#[serde(default, skip_serializing_if = "Vec::is_empty")]`. Being a `Scoped`-variant field, it is structurally unrepresentable on `Disabled`/`Target` (correct). It flows automatically to `HandlerConfig`/`ConsumerConfig`/`SessionConfig`/`FunctionConfig` (all carry `Option<Tenancy>`). Thread it onto the per-invocation `Scope` (add `unscoped_writes: BTreeSet<String>` to `Scope` at `orm.rs:480`, populated in `crates/boatramp-handlers/src/tenant.rs` `orm_scope` ~345) so `write_target` reads `self.unscoped_writes`. Keep it a per-invocation fact, NOT baked into the project-wide `table_key_map`.

## Guardrails (binding)
- **G1 (load-bearing):** the arm-3 allowlist fires **iff `resolve_table(T)==ResolvedScope::Unscoped && T ∈ self.unscoped_writes`, evaluated fresh every `write_target` call.** So under schema drift (list authored, then `T` re-declared `tenant`), the arm is inert → the normal tenant stamp applies. A `Tenant`/`TenantKeyed`/`TenantOrSession`/`TenantOrBase` table can NEVER be written unstamped via the list. The runtime resolve-gate is the primary guard; apply-time validation is defense-in-depth, NOT a replacement.
- **G2 (writes-only):** write-global / listed status changes NOTHING about reads. `ResolvedScope::SharedWritable` MUST behave read-identically to `Unscoped` at every read site (`read_pred` → `None`; `tenant_column_for`/`target_tenant_column` → `None`; `target_sql.rs` rewriter → no predicate; `graphql_gateway.rs` resolve usage → skipped like `Unscoped`). Add explicit tests asserting `read_pred(SharedWritable)==read_pred(Unscoped)==None`. The `all`↔`own` cap (`AccessMode`) is orthogonal and untouched.
- **HIGH — target × write-global REFUSED:** both new allow-arms are gated on `!self.is_target()`. A target-scope write to a write-global/listed table stays refused (`UnscopedWrite` or a dedicated `TargetWriteToGlobalTable`). `unscoped_writes` is naturally target-proof (it's a `Scoped`-variant field, a target route is `Tenancy::Target`), but the **write-global arm keys off the table**, so it MUST be explicitly `!is_target()`-guarded.

## CRITICAL — RESOLVED: global writes are ORM-only; raw SQL is fail-closed (Security block, 2026-09-26)
`write_target` is the choke point for the **ORM** write path only. The **raw-SQL** write path (`crates/boatramp-handlers/src/bindings/sql.rs::execute` → `apply_scope_marker` → `crates/boatramp-handlers/src/tenant.rs::sql_marker`) enforces tenancy DIFFERENTLY: it **requires** the `{scope}` marker for any non-`all` write (fail-closed if absent), and for RLS-backed Postgres sets a tenant GUC parsed from the INSERT VALUES. It never calls `write_target`, has no notion of `Unscoped`/write-global/`unscoped_writes`. boatramp's load-bearing invariant (`tenant.rs:9-11`) is that scoping binds BOTH surfaces.

**The original design proposed a raw-SQL write-global EXEMPTION mirroring the ORM. Security review (live-verified on MySQL 8.4) found that exemption to be a working cross-tenant WRITE bypass and BLOCKED it:**
- The exemption resolved the write's target table by parsing the raw statement with vanilla `sqlparser`, which treats MySQL/MariaDB `/*! … */` / `/*M! … */` **version-comments** as ordinary comments and IGNORES them — but the engine EXECUTES them. `UPDATE /*!50000 tenant_secrets */ oauth_state SET x=999` → the parser reports `oauth_state` (global → exempted, no predicate) → runs verbatim → the engine writes `tenant_secrets` (a tenant table) across ALL tenants.
- `INSERT INTO oauth_state (a) SELECT tenant_id FROM tenant_secrets` → exempted → the SELECT source ran UNSCOPED → cross-tenant exfiltration into the globally-readable table.

**Resolution (implemented): REMOVE the raw-SQL exemption entirely. Global writes are ORM-only.** With no raw-SQL exemption, a scoped raw-SQL write to any table (global or not) stays **marker-required**: it either carries the injected `tenant = ?` predicate (which binds whatever table the ENGINE actually executes — so even a comment-redirected write is scoped to the guest's OWN tenant, and an `INSERT … SELECT` source stays scoped) or, if `{scope}` is omitted, is refused. The ORM is the sole global-write path and is injection-immune (the guest names the table as a typed value — no comment lexing) and already scopes `INSERT … SELECT` sources. Cross-surface safety is satisfied by **REFUSAL** — raw SQL offers no weaker path than the ORM — NOT by replicating an unsound schema-blind parse. Concretely delivered:
- Deleted the write-global exemption branch in `apply_scope_marker`; deleted `HostTenancy::write_axis_is_global` and `boatramp_core::target_sql::extract_raw_write_table` (their sole caller was that branch). The `HostTenancy.unscoped_writes` field / `Scope.unscoped_writes` stay — they still drive the ORM `write_target`.
- The raw-SQL write path returns to the pre-#503 schema-blind marker-required behavior (safe): a global-table write via raw SQL is `tenant = ?`-scoped or refused. No global-table detection on the raw path (that detection was the unsound surface).
- The ORM half is UNCHANGED (`SharedWritable`, `Scope.unscoped_writes`, `write_target` arms, G1/G2/HIGH, activation validation, back-compat — the review verified these sound).
- **Cross-surface mutation gate** (`SCOPED UNSCOPED-WRITE CROSS-SURFACE OK`): asserts the ORM allows an unstamped global write while the RAW-SQL path does NOT exempt (marker-scoped/refused, never unscoped). Regression-locks the two attack statements above (raw `sql` binding, MySQL + SQLite) as refused-or-scoped, and mutation `m7_raw_exemption_reintroduced` FAILS the gate if the exemption is re-added.

## Back-compat / monotonicity
Every existing `Unscoped` table keeps write-deny; both mechanisms opt-in; worst case == today; `countries` (plain `unscoped`, no opt-in) stays refused. New `writable` field elides when false; new `unscoped_writes` elides when empty — pre-#503 configs serialize byte-identically. Note in CHANGELOG: a `writable:true` schema is forward-incompat (a pre-#503 binary can't read it → fail-closed `deny_all`, safe).

## Mutation-verified gate (behavioral — compiled-SQL / write-outcome, NOT structural; mutation-test EVERY assertion)
Marker e.g. `SCOPED UNSCOPED-WRITE CROSS-SURFACE OK`. Assertions each of which a specific mutation must FAIL:
- **M1** allowlist arm ignoring the set → a not-listed plain-`unscoped` write must still `Err(UnscopedWrite)`.
- **M2 (G1)** listed-but-now-`Tenant` table → INSERT/UPDATE MUST still stamp `tenant=<own>` (assert the stamp in compiled SQL); mutate the arm to fire before the `resolve==Unscoped` check → fails.
- **M3 (G2)** write-global must NOT widen reads → a sibling `tenant` table read under the same route still `tenant=<own>`; `read_pred(SharedWritable)==None`.
- **M4** plain-`unscoped`-not-listed write succeeding → deny-by-default eroded (assert refused).
- **M5** co-widening the read to `all` → `orm_scope(Read).mode==Own` unchanged; `narrows_within` still refuses a read widening.
- **M6 (HIGH)** target-scope write to a write-global table → MUST be refused.
- **M7 (CRITICAL)** raw-SQL / ORM parity → a write-global/listed table writable via BOTH bindings with identical unstamped outcome; a non-global table scoped on both; verified on Postgres AND libsql.
- **Live** (in `boatramp-storage` sqlx-live isolation battery): the canonical OAuth case end-to-end — `read:"own"` read of a tenant config table returns ONLY the own row (isolation intact) AND an INSERT into the write-global `oauth_state` succeeds with no tenant column; mutation M1 (drop the arm) → refused → fails; M-read (co-widen read to all) → sibling row leaks → fails.
